# Бейзлайн кодового агента на openJiuwen

Последовательный агент для соревнования: читает задачи, выбирает порядок,
выполняет действия модели через Bash/Python и файлы, сохраняет `answer.txt`.
Рабочие данные каждой задачи копируются в отдельную временную папку.

Новая версия — **state-v2**, запуск через `run_solution.py` или Docker. Профиль
в `configs/recommended.json`: JSON Schema для действий; для data/math/search —
ограниченная память прогресса и наблюдений с происхождением. Coding использует
простой state: расширенная память ухудшила его результаты в полном эксперименте.
Профиль выбирается по публичному типу задачи, без ветвлений по ID и эталонам.
Измерения и ограничения: [reports/state-v2.md](reports/state-v2.md).
В двух полных прогонах: **24/26 и 23/26** выполнимых задач против **21/26 и 22/26**
у исходного state, средний расход ниже на **28.6%**. Каждый прогон включает также
три невыполнимых контроля; это знакомый набор, не независимый holdout.
Проверенный готовый образ: `huawei-state-v2:tested`.
Таблица всех задач и всех версий: [runs/state-v2/report.md](runs/state-v2/report.md).

Быстрый запуск на свежей копии задач с уже установленными Docker-зависимостями:

```bash
python3 scripts/prepare_run.py --source task-dir --dest runs/my-state-v2/tasks
python3 scripts/run_docker.py --tasks-dir runs/my-state-v2/tasks --budget 20000
```

`run_docker.py` использует текущие исходники через mounts и существующий образ
`huawei-baseline:tested`. Для воспроизводимого запуска без mounts исходников
используйте упакованный образ из отчёта. `.env` читает только Docker.
Параметры после профиля переопределяют его настройки. `run_agent.py` сохраняет
прежние defaults для контрольных сравнений; таблицы старых defaults ниже
относятся к нему. Новый профиль: 2500 на задачу, 24 шага, 900 output tokens,
180 секунд; reasoning отключён. Общий `--budget` задавайте по реальному лимиту.

Текущая основная модель — `qwen3.8-27b-noreason`.
`--reasoning-budget 0` по умолчанию запрещает вызовы reasoning-моделей;
для их исследования нужен явный положительный лимит, в который входит полная
стоимость таких вызовов. Контрольные `history`/`hybrid` сохранены.
Реальные результаты, включая неуспешные эксперименты: [reports/state-focus.md](reports/state-focus.md).

## Правило сравнительных прогонов

После отдельного воспроизведения прежнего успешного набора все последующие
проверки качества агента проводятся на полном реестре: **29 уникальных вариантов
из 37 исходных папок** (8 исходных задач соревнования и все отличающиеся
сгенерированные примеры). Точные копии объединены с сохранением источников.
Реестр: [benchmarks/all-v1/catalog.md](benchmarks/all-v1/catalog.md).

Основной запуск для дальнейших сравнений:

```bash
python3 scripts/benchmark.py --suite all --comparison solution --out runs/all-next-v1 --repetitions 2
```

`--comparison solution` сравнивает исходный state с алгоритмическими флагами
`configs/recommended.json`; модель, бюджет и остальные лимиты одинаковы.
Порядок чередуется между повторами. На 29 задачах два повтора двух версий имеют
верхний лимит 290000 выходных эквивалентов; фактический расход обычно ниже.
`--comparison memory` (старый default) сохраняет сравнение off/bounded.
Новый сравнительный прогон платный, поэтому его не нужно запускать для
обычной подготовки задач или проверки синтаксиса.

По умолчанию suite=all. Перед запуском проверяется актуальность полного реестра;
новые или изменившиеся задачи требуют пересборки в новую папку и указания
`--catalog`. Лимиты одинаковы между режимами; default общего бюджета полной серии
равен числу задач, умноженному на task-budget. Скрипт заранее печатает плановый
верхний расход всех серий. `--resume` использует уже завершённые серии без
повторения платных вызовов. Бюджетная остановка одной серии не отменяет остальные.

В results.json и report.md обязательна отдельная строка каждой задачи и каждого
повтора: SOLVED, WRONG_ANSWER, SKIPPED, IMPOSSIBLE_SKIP, STOPPED, ERROR,
NOT_ATTEMPTED. Баллы и число решённых задач показываются раздельно. Частичный
прогон явно помечается частичным. Узкие старые experiment-скрипты сохранены
для воспроизводимости прежних работ, а не как замена полного сравнения.

## Установка и конфигурация

Нужен Python 3.11–3.13. Прямая зависимость — `openjiuwen==0.1.19`.

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env
# Отредактировать .env локально: адрес прокси и ключ.
set -a
source .env
set +a
.venv/bin/python scripts/check_environment.py
```

`.env` не загружается самим приложением и исключён из Git и Docker.
Ключ не выводится диагностикой и не передаётся процессам инструментов.
`LLM_BASE_URL` — полный базовый URL, включая `/v1`, если этого требует прокси.
Можно передать и полный URL с `/chat/completions`.
Адаптер предполагает Bearer-аутентификацию и JSON Chat Completions.
Совместимость с реальным прокси проверена платными вызовами в Docker; ключ хранится локально в .env.

## Подготовка и запуск

Работайте на копии: coding-задачи меняют исходники. Подготовка удаляет поля
`expected` и `check` из копии метаданных, чтобы эталоны не попадали агенту.

```bash
.venv/bin/python scripts/prepare_run.py --source task-dir --dest runs/first/tasks
.venv/bin/python run_agent.py --tasks-dir runs/first/tasks --dry-run
.venv/bin/python run_agent.py --tasks-dir runs/first/tasks --budget 20000
.venv/bin/python scripts/evaluate.py --reference task-dir --tasks-dir runs/first/tasks --out runs/first/evaluation.json
```

`20000` — пример локального лимита, не известный бюджет соревнования.
Без `--budget`/`TOKEN_BUDGET` общий лимит контролирует только прокси;
лимит на одну задачу остаётся активным. Планирование с `--dry-run` не требует
openJiuwen, ключа, сети и ничего не записывает.

Для отдельной задачи: `--task-id math_0004`; параметр можно повторять.
Для пропуска уже записанных ответов: `--resume`. Это НЕ восстановление общего
бюджета: при повторном запуске передайте оставшийся бюджет. Без `--resume`
программа отказывается работать при существующих ответах.

Основные параметры:

| Параметр | По умолчанию | Назначение |
|---|---:|---|
| `--model` | `qwen3.8-27b-noreason` | Одна из четырёх разрешённых моделей |
| `--max-steps` | 12 | Число вызовов модели на задачу |
| `--task-budget` | 8000 | Лимит задачи в эквивалентных выходных токенах |
| `--max-output-tokens` | 1500 | Верхняя граница ответа модели |
| `--time-limit` | 3500 | Общее время в секундах |
| `--task-seconds` | 300 | Время на задачу |
| `--request-seconds` | 90 | Таймаут HTTP-запроса |
| `--tool-seconds` | 20 | Таймаут команды |
| `--history-chars` | 24000 | Размер сохраняемой недавней истории |
| `--reasoning-usage` | `included` | `separate`, если reasoning НЕ включён в completion/output tokens |
| `--max-tokens-field` | `max_tokens` | Альтернатива: `max_completion_tokens` |

## Результаты и оценка

Главный артефакт — `<task>/answer.txt`; дополнительно ответ зеркалируется в
`workspace/answer.txt`, если workspace есть. Это учитывает неоднозначность
регламента и примеров. Для coding сначала проверяются неизменность тестов
и `python3 test_mylib.py`, затем переносятся исправленные файлы и пишется `DONE`.
Текущий валидатор coding рассчитан на точку входа из предоставленных примеров.

Логи запросов, ответов, инструментов и расхода: `<tasks>/.baseline/<run-id>.jsonl`.
Сводка сохраняется после каждой задачи в `<run-id>.json`; `--out` меняет её путь.
`--logs-dir` меняет папку логов. Она должна быть доступна для записи.
Сводка `submitted` означает сдачу ответа, а не прохождение скрытой проверки.
Оценщик читает оригинальные `expected/check`, проверяет ответы и код на копии,
возвращает exit code 0 при успехе всех задач и 1 при неверных/отсутствующих ответах.
Код выхода агента: 0 — очередь обработана (возможны пропуски), 2 — ошибка/остановка.

## Архитектура и точки расширения

- `run_agent.py`: параметры, очередь, общий бюджет и сохранение сводки.
- `baseline/workflow.py`: реальный workflow openJiuwen с компонентом решателя.
- `baseline/solver.py`: цикл модель → действие → результат; контекст и сдача.
- `baseline/client.py`: HTTP-адаптер и извлечение usage.
- `baseline/tools.py`: чтение/запись файлов, Bash, таймауты и ограничение вывода.
- `baseline/core.py`: структура задачи, учёт расхода, приоритет и атомарная запись.
- `scripts/prepare_run.py`, `evaluate.py`, `check_environment.py`: обслуживание.

API workflow сверено с исходниками [openJiuwen v0.1.19](https://github.com/openJiuwen-ai/agent-core/blob/v0.1.19/openjiuwen/core/workflow/workflow.py)
и [WorkflowComponent](https://github.com/openJiuwen-ai/agent-core/blob/v0.1.19/openjiuwen/core/workflow/components/component.py).
Инструменты передаются текстовым JSON-протоколом; нативный tool calling от прокси
не требуется. Промпт описывает `bash`, `read`, `write`, `final`, `skip`.

Начальная стоимость по типу: math=1, search=2, data_analysis=2, coding=5;
приоритет — reward / стоимость. Это эвристика, ещё не обученный оценщик.
Невыполнимость: явный `skip` модели или достижение лимита задачи. Обученного
классификатора и собранного корпуса траекторий пока нет; логи будущих прогонов
служат заготовкой такого корпуса. На задачу одна сессия, параллельности пока нет.

Расход = input / 10 + output. Кеш не вычитается. По умолчанию reasoning уже
включён в output; режим `separate` добавляет его ровно один раз. Семантику usage
нужно сверить с прокси. До запроса вход оценивается по числу UTF-8 байт с запасом;
это эвристика, не точный токенизатор. При отсутствии usage резервируется весь
лимит ответа, оценка помечается как приблизительная. Финальный бюджет авторитетно
контролирует прокси. Сетевые ошибки не повторяются автоматически: после таймаута
невозможно узнать, были ли списаны токены. Ошибка прокси (HTTP-код, транспорт,
неверный ответ) или неожиданное исключение пропускает только текущую задачу:
после паузы 5·N секунд агент переходит к следующей. Прогон останавливается после
3 таких сбоев подряд, а также сразу — по времени или общему бюджету.

Временная папка и проверки путей для read/write не являются OS-песочницей:
Bash запускает произвольный код. Для запусков модели используйте Docker.
Контейнер — граница изоляции от хоста; разные задачи внутри него не имеют
отдельной файловой/сетевой изоляции. Полный доступ к эталонам не надо монтировать
в локальный контейнер; монтируйте подготовленную копию задач.

## Docker

```bash
docker build -t hack:latest .
docker run --rm \
  -e LLM_BASE_URL -e LLM_API_KEY \
  -v "$PWD/runs/first/tasks:/data/tasks:rw" \
  --read-only --tmpfs /tmp:rw,size=2g -e HOME=/tmp \
  --cap-drop ALL --security-opt no-new-privileges \
  --cpus 4 --memory 16g --pids-limit 512 \
  --workdir /app --entrypoint python hack:latest \
  /app/run_agent.py --tasks-dir /data/tasks --budget 20000
```

У организаторов добавляется `--network hack-net`; локально такая сеть может
отсутствовать. Обычный Docker network сам по себе не запрещает внешний интернет.
При запуске ничего не устанавливается и не скачивается. Для официальной команды
достаточно `--tasks-dir`; обязательного `--budget` нет, как и в регламенте.
Базовый тег и openJiuwen зафиксированы. Проверенные Linux-зависимости зафиксированы в `requirements.lock`, Docker использует этот файл.
Проверенная архитектура — Linux ARM64; AMD64 отдельно не проверялась.

## Эксперимент SKILL.state

`--context-mode history|state|hybrid` выбирает стратегию памяти. По умолчанию
сохранён history. State передаёт инструкцию, ограниченный JSON и последнее
наблюдение; hybrid добавляет последний обмен (параметр `--hybrid-turns 0..2`).
Схема общая для неизвестных типов: facts, hypotheses, rejected, open_questions,
artifacts. Это заметки модели, не доказанные факты. Служебные поля бюджета
модель менять не может. Патчи применяются атомарно после проверки структуры;
отсутствующие ключи сохраняются, null удаляет отдельную запись. Лимит — 8 записей
на поле, 240 символов на значение и `--state-chars` (6000) на всё состояние.
Полные события сохраняются в JSONL; state-снимки предназначены для анализа,
не являются восстановлением файловой системы после сбоя.

```bash
python3 scripts/make_experiment.py --out experiments/custom --seed 123
python3 scripts/experiment.py --reference experiments/custom --out runs/custom-experiment
```

Вторая команда делает реальные платные запросы: максимум 4000 эквивалентных
выходных токенов на режим, всего 12000; лимит задачи 1600, максимум 8 шагов.
Она использует существующий Docker-образ и подключает текущий код через mounts.
Ключ загружается из `.env`, URL при запуске явно установлен на официальный
`https://api.neuraldeep.ru/v1`. Эталоны НЕ монтируются в агент.

Первый набор `experiments/skillstate/dev` создан с seed=41; holdout с seed=97
оставлен для следующей проверки. Это разные данные одних генераторов, не
независимые семейства задач. Для оценки универсальности потребуются отдельные
семейства, более длинные задачи и несколько повторов. Правильный skip не даёт
баллы, но отдельно измеряется как экономия на невыполнимой задаче.
Результаты содержат score, реальный input/output usage, стоимость, число вызовов,
время и ошибки инструментов/валидации. Не начатые из-за бюджета задачи отмечаются
not_attempted; их нельзя интерпретировать как ошибку решения модели.

## Единый протокол ответов (unified-v1)

По умолчанию `--response-protocol unified` для всех режимов памяти. Формат:

```json
{"action":{"action":"read","path":"library.py"}}
```

При изменении памяти можно добавить `state_patch`:

```json
{"action":{"action":"read","path":"library.py"},"state_patch":{"hypotheses":{"h1":"Check empty input"}}}
```

Поле `state_patch` необязательно; отсутствие и `{}` означают отсутствие изменений.
В `state`/`hybrid` сохраняется прежнее слияние с null-удалением и прежние лимиты.
В `history` постоянное состояние не ведётся: модель получает инструкцию опускать
патч, а случайно выданный корректный патч проверяется, но не сохраняется.
Все три режима получают одинаковый system prompt, примеры действий, парсер
и проверку структуры ответа. Полные имена инструментов и правила final/skip общие.
В истории/hybrid действия тоже показываются во вложенной оболочке.

Строгий разбор отклоняет пояснения вокруг JSON, дубли ключей, неизвестные поля,
неизвестные действия и неверные типы аргументов. Один целый блок ```json допускается
парсером одинаково во всех режимах, хотя промпт просит чистый JSON.
Ошибочный ответ не выполняет инструмент и не меняет память. Обратная связь
о валидации не стирает последнее полезное наблюдение. Ошибки формата получают
отдельные JSONL-события `response_error`.

### Контрольные конфигурации

Старый контекст и промпт сохранены в `baseline/legacy_context.py` и `SYSTEM`
в solver. Их хеши закреплены регрессионным тестом. Не меняйте их при настройке
unified. Предыдущие эксперименты, в которых параметра ещё не было, использовали
legacy; исходные результаты не переписаны.

| Конфигурация | Аргументы |
|---|---|
| Прежний history | `--context-mode history --response-protocol legacy` |
| History с общей оболочкой | `--context-mode history --response-protocol unified` |
| Прежний state | `--context-mode state --response-protocol legacy` |
| State с общим парсером | `--context-mode state --response-protocol unified` |

Параметр поддерживает и `scripts/experiment.py`; для каждого протокола выбирайте
отдельную новую папку `--out`. Протокол записывается в сводку агента и результаты
эксперимента; `response_errors` отдельно считает отклонённые ответы.

Офлайн-проверка: все 34 теста прошли в Docker без сети, включая воспроизведение
13 принятых ответов из успешного сложного state-прогона. Состояния совпали.
Вывод: `UNIFIED_PROTOCOL_TEST_RESULTS.txt`. Это проверка совместимости кода,
не измерение качества модели после изменения промпта. Новых платных прогонов
на данном этапе не проводилось. Расчёт бюджета, модели и лимиты не менялись.

Для проверки текущего кода существующим образом используйте mounts из примера
выше; при новой сборке Dockerfile автоматически включает protocol.py и
legacy_context.py. Старый собранный образ сам по себе исходники не обновляет.

## Оценка входа и резерв завершения

Новые независимые параметры (поддерживаются также scripts/experiment.py):

| Параметр | По умолчанию | Значение |
|---|---|---|
| `--input-estimator` | `calibrated` | `legacy` сохраняет UTF-8 bytes+256; calibrated учится по реальному usage отдельно для модели |
| `--budget-policy` | `reserve` | `off` отключает фазы и резерв завершения |
| `--finish-output-tokens` | 256 | Лимит output финального запроса, не выше общего max-output-tokens |
| `--finish-seconds` | 20 | При меньшем остатке времени переходить к сдаче |

До первого ответа calibrated использует прежнюю консервативную оценку. Затем
берёт максимальное отношение prompt_tokens/bytes последних 32 наблюдений модели,
добавляет 15% и 64 токена. Независимый лексический запас считает цифры и знаки
пунктуации плотнее обычного текста, защищая от переноса текстовой калибровки на CSV.
Это эвристический прогноз, НЕ точный токенизатор Qwen и НЕ гарантированная верхняя
граница. Он не использует локальные нейросети, скачивания или платные запросы.
Фактический расход по-прежнему считается по полному input usage без скидки кеша.
При отсутствии usage новая калибровочная точка не создаётся.

Reserve удерживает оценку входа финального вызова / 10 + finish-output-tokens + 64
эквивалентных токена. Рабочие вызовы могут тратить только оставшуюся часть.
Если она не вмещает запрос, runtime переходит к финальному запросу до HTTP-вызова.
За два шага до лимита агент получает фазу verify, на последнем шаге — submit.
В submit разрешены только final/skip, включая блокировку действия до применения
state_patch. Модель должна сдавать ответ только при достаточных основаниях.
Runtime не придумывает ответ и не ставит DONE автоматически; для coding прежняя
проверка неизменности и прохождения тестов остаётся обязательной.

Резерв — оценочный: новый вывод инструмента и изменения текста могут изменить
цену финального запроса, а модель может игнорировать предупреждение о verify.
Наличие резерва само по себе не гарантирует успешную сдачу. Для длинных ответов
параметр finish-output-tokens следует увеличить. Фактический лимит контролирует
прокси, бюджет нельзя расходовать после его исчерпания.

Полное воспроизведение старой конфигурации теперь требует трёх переключателей:

```bash
python3 run_agent.py --tasks-dir runs/example/tasks \
  --response-protocol legacy --input-estimator legacy --budget-policy off
```

Для чистого сравнения формата ответов фиксируйте для обоих протоколов
`--input-estimator legacy --budget-policy off`. Для абляции оценки входа фиксируйте
протокол и `--budget-policy off`, меняйте только input-estimator. Для абляции
резерва фиксируйте протокол и оценщик, меняйте только budget-policy.

События `request/response` содержат input_estimate и ошибку относительно usage;
`completion_policy` записывает фазу и резерв. В сводке записаны все переключатели.
Проверка без API: 44 теста Docker, BUDGET_POLICY_TEST_RESULTS.txt.
Ретроспективная проверка оценки: reports/input-estimator-replay.json, 85 вызовов.
MAE снизилась с 3862.7 до 1568.2 токена; недооценок в этом наборе 0, до холодного
старта оценка не менялась. Защита числовых данных разработана после анализа этих
логов, поэтому это НЕ независимая валидация и НЕ доказанная экономия бюджета.
Новые реальные LLM-прогоны на данном этапе не выполнялись.

## Селектор модели/памяти и предварительный скрининг

Поддерживаются все четыре разрешённые модели. `--selection-policy fixed` по
умолчанию сохраняет выбранные --model/--context-mode. В shadow рекомендации
только логируются. В learned рекомендация выбирает пару модель+память перед
задачей; во время задачи модель не переключается. Селекция/прогноз не вызывают LLM.

```bash
python3 scripts/train_portfolio.py --runs runs --out models/portfolio-v1.json
python3 run_agent.py --tasks-dir runs/example/tasks \
  --selector-artifact models/portfolio-v1.json --selection-policy shadow
```

Требования Python/openJiuwen прежние. Для существующего контейнера дополнительно
монтируйте models в /app/models:ro; при новой сборке Dockerfile включает models.
Каталог моделей проверяется scripts/model_inventory.py через GET /models, без
генераций; наличие в каталоге не доказывает разрешения генерации/доступную квоту.

Первый предиктор — простой эмпирический контроль, НЕ полная реализация TokenCast
и НЕ обученная калиброванная вероятность. Он группирует повторные попытки одной
нормализованной инструкции, использует ближайшие группы того же типа задач и
раздельно оценивает успешность при заданных лимитах, стоимость попытки до остановки
и стоимость успешного завершения. Сортировка reward*P/expected_attempt_cost —
эвристика. Порог поддержки — минимум 3 группы и наличие успешных примеров.
Очень отличающиеся по размерам задачи (log-feature distance >4) и несовместимые
настройки бюджета/протокола дают fallback. Радиус — эвристика, не обученная граница.
Неподдержанные кандидаты не получают выдуманной оценки. Настройки finish-политики
учитываются; если policy off, её неиспользуемые finish-параметры нормализуются в null.

Доступные кандидаты ограничиваются --candidate-models и --candidate-modes. Эти
списки ограничивают рекомендации; fallback остаётся явно указанной исходной
--model/--context-mode. В learned порядок задач использует оценку удельной выгоды,
а для неподдержанных задач — исходную эвристику, приведённую к масштабу токенов.
Это ещё не оптимальный стохастический планировщик. Рекомендация пересчитывается
перед задачей с учётом оставшегося общего бюджета.

При наличии артефакта прогноз оставшегося расхода записывается после каждого
шага в remaining_forecast. Это эмпирические квантили успешных траекторий по
близким calls/spent; forecast не передаётся модели и НЕ останавливает задачу.
Отсутствующие данные явно дают supported=false. Никакого SFT/локальной нейросети нет.

### Как учитываются невыполнимые задачи

`--screening shadow` по умолчанию записывает упомянутые отсутствующие файлы,
а также повторения одного действия с тем же результатом (от трёх повторений).
Ничего автоматически не отбрасывается. Выход `verdict=unknown, auto_reject=false`
обязателен: упомянутый файл может быть выходным, а зависимость — исправимой.
Текущие реальные причины пропуска остаются раздельными: skip модели, лимит
шагов, бюджет, время, ошибки инфраструктуры. Эти события НЕ становятся меткой
принципиальной невыполнимости. Автоматический фильтр надо отдельно обучать и
валидировать по потерянным баллам на выполнимых задачах. Поле confidence модели
само по себе не является доказательством. --screening off отключает новые сигналы.

### Данные и качество

Сборщик читает только results.json с внешним passed (submitted не считается
успехом). Признаки извлекаются из task_start до решения; для старых логов берётся
начальный список файлов из запроса. Размеры исходных файлов в старых логах
неизвестны и помечаются null, вместо чтения уже исправленного кода. expected и
check не входят в признаки. Бюджетные неуспехи не используются как стоимость
успешного решения; положительные префиксы отдельно обучают remaining-оценку.

В portfolio-v1: 26 попыток, 8 групп инструкций, одна модель
qwen3.8-27b-noreason. При исключении целой группы все 26 прогнозов отказались
от рекомендации из-за нехватки подходящих данных. Это НЕ доказанная успешность
селектора. Группировка нормализует числа в инструкции, но не доказывает независимости
семантических семейств; для финальной проверки нужна ручная/генераторная группировка.

### Сбор матрицы четырёх моделей

scripts/experiment.py принимает --models с разрешёнными именами. Сочетания
model x context-mode запускаются последовательно на отдельных копиях задач,
с одинаковыми лимитами и внешней проверкой, включая hidden_test.py.
При одной модели прежний формат папок сохраняется. С несколькими — model__mode.
ВАЖНО: общий верхний расход равен mode-budget * число моделей * число режимов.
На предыдущем этапе матрица ещё не запускалась; теперь короткий прогон выполнен.
Результаты и ограничения: reports/state-focus.md, runs/combined-v1/seed/results.json.

Артефакты: models/portfolio-v1.json, models/portfolio-v1.report.json,
reports/portfolio-stage3.md. Проверка без API: 57 тестов Docker,
PORTFOLIO_TEST_RESULTS.txt. CLI и интеграционный тест проверяют, что выбранная
модель действительно попадает в HTTP payload, а предупреждение скрининга не
блокирует решение.


## Экспериментальная оркестрация и основной state

`--orchestration boundary` включает один платный выбор между light/full;
`--experience-file models/experience-combined-v1.json` добавляет одну процедурную
карточку. Сборка: `scripts/build_experience.py --help`. Это исследовательские
приближения, эффект компонентов по отдельности пока не измерен.
`--pacing weighted` жёстко делит бюджет — в последнем сравнении такая комбинация
провалилась. `--pacing advisory` передаёт мягкий ориентир, без урезания квоты;
живой сравнительный тест для него пока не проведён. `--loop-policy finish`
экспериментально переводит повторяющиеся действия к завершению.
Все эти параметры по умолчанию выключены. Для обычного state они не нужны.

Пример нового ограниченного state-only прогона (папка результата должна быть новой):

```bash
python3 scripts/experiment.py --reference experiments/state-broad-v1 \
  --out runs/my-state-test --modes state --models qwen3.8-27b-noreason \
  --mode-budget 8000 --task-budget 1600 --max-steps 16 \
  --max-output-tokens 900 --task-seconds 150 --reasoning-budget 0
```

Скрипт запускает Docker с актуальными исходниками через read-only mounts,
изолированными копиями workspace и внешним оцениванием. Общий лимит матрицы
умножается на число моделей и режимов. `--tool-output-chars` позволяет отдельно
исследовать размер наблюдений; по умолчанию 12000, как у агента. Меньший лимит
пока не показал улучшения. Новые результаты с нестандартным размером вывода
не смешиваются сборщиком с обучающими данными старого portfolio.

Последняя полная проверка: 67 тестов Docker, STATE_FOCUS_TEST_RESULTS.txt.


## Буфер наблюдений state

`--observation-memory bounded` включает отдельную память фактических результатов
инструментов в unified state/hybrid. Заметки `state_patch` сохраняют прежнюю схему.
По умолчанию новый буфер пока выключен; контроль — `--observation-memory off`.
Буфер автоматически хранит до четырёх коротких записей, отдавая приоритет двум
последним результатам Bash. Последнее наблюдение не дублируется в контексте.
`--observation-memory-chars 3000` ограничивает весь дополнительный JSON-блок
в символах, включая метаданные; допустимый минимум 1024. Это не лимит токенов.
Переполнение приводит к вытеснению записей, полный вывод остаётся в host trace.
Укороченные строки явно перечислены в `excerpted_fields`; исходное `truncated`
инструмента, таймаут и returncode сохраняются. Буфер не проверяет правильность ответа.

Свежесть определяется по хешу содержимого, путей и прав файлов всей рабочей
папки после каждого инструмента. Изменения через Bash также учитываются.
`stale` консервативно означает изменение каких-либо файлов; зависимость конкретного
результата от изменённого файла не установлена. При неполном аудите — `unknown`.
Лимиты одной проверки: 4096 записей, 32 MiB файлов, 0.5 секунды. Симлинки и
специальные файлы не читаются; аудит в таком случае считается неполным.
Свежесть не распространяется на время, внешнее состояние или смысл вычисления.
Bash с изменением файлов получает unknown для связи вывода с итоговой версией.

Сравнительный API-тест: `python3 scripts/run_observation_memory_live.py`.
Он создаёт новую папку, выполняет off/bounded на двух знакомых задачах в Docker,
суммарный верхний бюджет 6400. Повтор требует нового `--out`.
Для общего runner доступны те же `--observation-memory` и
`--observation-memory-chars`. Результаты конфигураций не смешиваются с историческим
portfolio: параметры памяти входят в ключ совместимости.


Результаты внедрения буфера: [reports/observation-memory-v1.md](reports/observation-memory-v1.md).
79 тестов прошли в Docker. В изолированном API-тесте сохранённый результат
использован правильно; полное сравнение на двух задачах не дало прироста баллов.
Поэтому включение остаётся явным: `--observation-memory bounded`.
